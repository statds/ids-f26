Collaborative Notes

The Fall 2026 collaborative notes supplement the instructor-authored Introduction to Data Science book. They give students practice explaining data-science concepts and working through a Git and GitHub review process.

The notes are maintained in the ids-f26 repository. Students contribute through topic branches and pull requests. The repository contains two kinds of presentation. A topic presentation explains a method or idea and belongs under topic/; a final-project presentation reports an original project and belongs under final/.

Each topic presentation needs a short catalog entry in its relevant topical chapter. Final-project presentations are collected in the Final Project Presentations chapter. In both cases, the slide deck is the substantive contribution; contributors do not need to rewrite slides as prose.

The topical chapters and final-project chapter organize and link to presentations; they do not duplicate the instructor book.

Clone and Render the Notes Locally

Keep a local copy of these notes so that you can render presentations before opening a pull request. Place the ids-book and ids-f26 repositories in the same parent folder. If you plan to contribute, fork statds/ids-f26 on GitHub first, then clone your fork. Replace GitHub_Username below with your GitHub username:

cd path-to-your-course-work
git clone https://github.com/GitHub_Username/ids-f26.git
cd ids-f26
git remote add upstream https://github.com/statds/ids-f26.git
git remote -v
git status

If you only want a local copy for reading and rendering, clone the shared repository directly instead:

git clone https://github.com/statds/ids-f26.git
cd ids-f26

Use the course Python environment that you already chose while working through the instructor book. Do not create another virtual environment or install packages inside ids-f26. From the ids-f26 repository, set ENVIRONMENT_DIRECTORY to that environment’s path and activate it:

ENVIRONMENT_DIRECTORY=/path/to/your/environment

# macOS or Linux
source "$ENVIRONMENT_DIRECTORY/bin/activate"

# Windows with Git Bash
source "$ENVIRONMENT_DIRECTORY/Scripts/activate"

Confirm that the selected interpreter is the course environment before rendering:

python --version
which python
make check-tools

Render the notes and all accepted presentations with:

make render

Quarto writes the local site to _book/index.html. Open that file in a browser and inspect the page or slides before requesting review. While developing one presentation, render only that source file:

make render-one FILE=topic/last-name-topic/index.qmd

The _book/ directory is generated output and must stay out of commits. If a render fails because a package is missing, first verify the active interpreter and ask the instructor before adding a dependency to the shared course environment.

Presentation Expectations

A presentation should ordinarily contain:

  • a motivating question or explanation of why the topic matters;
  • the main concept, method, or tool;
  • at least one minimal, reproducible example;
  • an interpretation of important output;
  • limitations, common mistakes, or situations where the method is unsuitable;
  • two or three principal takeaways; and
  • sources and image attribution.

Slides should support an oral presentation without becoming a transcript. Use readable text, explain displayed code and output, and generate results from executable code when practical. Link to relevant material in ids-book instead of repeating substantial instructor-authored exposition.

The example Quarto presentation demonstrates the expected directory layout and basic slide conventions. The presentation-skills example discusses storytelling, visual design, delivery, and evidence-based claims.

Final Presentation Peer Evaluation

Each student evaluates every other presenter using the same three criteria. Rate each criterion on a 5–1 scale, where 5 means excellent and 1 means poor. Do not evaluate your own presentation. Base each rating on evidence from the presentation and add a brief comment explaining the rating.

Use the following general scale:

  • 5 – Excellent: exceptional, complete, and convincing;

  • 4 – Strong: clear and effective, with only minor weaknesses;

  • 3 – Adequate: generally satisfactory, but with noticeable gaps;

  • 2 – Limited: partially successful, but with substantial weaknesses; and

  • 1 – Poor: missing, seriously flawed, or not understandable.

  • Domain: Does the presentation motivate the work adequately? Does it explain what the project is for and why it matters? Does it place the project in context by reviewing relevant existing work appropriately?

  • Methods: Are the variables meaningfully constructed? Are the methods appropriate for the problem, and are they adapted effectively to the application? Are the computational methods used appropriately? Does the presentation acknowledge important limitations?

  • Presentation: Is the presentation clear, professional, and informative for a general audience? Are the findings interpreted effectively in nontechnical language? Do the tables and figures communicate the intended information clearly?

Topic Presentations

The private course syllabus contains the official assessment policies for topic presentations. This public chapter also provides the working rubric so that contributors understand what makes a strong presentation, pull request, and revision.

Topic Presentation Rubric

Topic presentations are worth 20 points. A topic presentation is a focused teaching contribution, not a final research project; original data, advanced methods, and novel findings are not required.

  • Approval and preview: 4 points. The topic is focused and appropriate, the proposed approach is approved, the preview is submitted on time, and the deck is sufficiently complete to review. Sources should be identified, and examples should run when computation is part of the presentation.
  • Oral presentation: 10 points. The presentation motivates the topic and explains its main idea accurately (3 points), develops a useful example and interprets its output correctly (3 points), discusses limitations, common mistakes, and specific takeaways (2 points), and uses readable slides with clear, organized, and engaging delivery (2 points).
  • Pull request and revision: 6 points. The source is organized, reproducible, and properly attributed (2 points); the contributor responds to review with a meaningful revision and maintains a focused pull request (2 points); and the final source and topical catalog entry are complete and correctly linked (2 points).

Contributing to the Collaborative Notes

See the repository’s contribution guide for the detailed presentation, Git, and pull-request workflow.

Use the following workflow:

  1. Synchronize your local repository with the shared repository.
  2. Create and switch to a topic branch.
  3. Copy and adapt the example directory into topic/ or final/, according to the kind of presentation.
  4. Add a short entry to the appropriate topical chapter, or add the final project to the Final Project Presentations chapter.
  5. Activate the course Python environment when computation is required.
  6. Render and review the presentation locally.
  7. Make small commits with informative messages.
  8. Push the branch and open a pull request.
  9. Respond to review and revise the contribution as needed.

Before requesting review, check that the contribution:

  • is original and properly attributes all sources;
  • follows the example presentation structure and has a matching chapter entry;
  • follows the repository’s file-naming and source-writing conventions, including a line width under 80 characters for prose and Markdown source;
  • uses small, meaningful commits throughout the work rather than one large final commit, without creating empty or artificial commits;
  • uses BibTeX for scholarly references;
  • avoids unnecessary external files and large data files;
  • uses only images that may legally be redistributed;
  • records any new Python dependencies in the environment specification; and
  • renders successfully on the contributor’s computer.

Pull requests contain source files, not rendered output. After a pull request is reviewed and merged, the instructor renders the complete notes and all accepted presentations and publishes the unified site.

Editorial acceptance and course assessment are separate decisions. Assessment emphasizes the contribution process, including meaningful work, appropriate Git usage, responsiveness to review, reproducibility, and constructive feedback to classmates.

Assignment Workflow

Graded work is submitted through the designated Classroom 50 repository, not through the instructor book or collaborative-notes repository.

Each assignment submission must use one .qmd source file that solves all assigned problems. Label every problem clearly inside that file so that the source and rendered PDF are easy to navigate. Use the homework template as the starting point for the required structure.

Follow the detailed Git workflow in Project Management, especially Exercise 2.7. That workflow explains how to inspect a repository, create a branch, stage named files, review diffs, write meaningful commits, inspect history, and preserve evidence of the work.

Fall 2026 assignment requirements are:

  1. Accept the assignment through the course site and clone the resulting Classroom 50 repository.
  2. Develop the single .qmd source file on a descriptive branch, solving all assigned problems and labeling them clearly.
  3. Make at least ten small, meaningful commits for every assignment. Do not create empty commits or split meaningless changes merely to reach ten. Each commit should record a real development step and use an informative, imperative message.
  4. Preserve the complete branch history. Record the branch name, commit hashes and messages, and concise command results in the assignment source or wherever the assignment specifies.
  5. Push the branch and render the assignment before submitting the PDF through the designated course workflow.

The ten-commit requirement applies to each assignment repository, not to the semester notes repository as a whole. Graded assignments remain private in Classroom 50 and are not submitted as public pull requests unless an assignment specifically says otherwise.

Keep generated files out of the repository unless the assignment explicitly requests them. Use Git from the command line rather than GitHub’s file-upload interface, and never commit credentials or large data files.
